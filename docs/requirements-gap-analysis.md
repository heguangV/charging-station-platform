# 需求差异、扩展与未确定问题

## 1. 分析依据

本清单以 [软件需求规格说明书](01-requirements-specification.md) 的文字条款为主，以原始项目要求书补充总体背景，并对照此前已确认的 Android、云端、PostgreSQL、即时排队与安全方案。

处理原则：

- SRS 已写明的功能、异常流、指标和截图不再当作普通待选项。
- 可兼容的增强直接列入扩展路线。
- 改变验收平台、主流程、数据库或架构的决定必须明确确认。
- 本地教学演示与公网运行采用不同安全配置。

## 2. 新 SRS 已明确的内容

以下问题不再需要从零设计：

- 用户端和管理端的页面尺寸、主要控件、异常提示与截图要求。
- 手机验证码登录、自动注册、默认昵称/头像、充值范围和头像限制。
- Haversine 距离、腾讯地图两级降级导航和三种出行方式。
- 15 分钟预约、每秒计费、时间倍率 60、进程重启后恢复和事务结算。
- 营收折线/柱状图、设备饼图、健康度公式、远程重启 2 秒和 CRUD 范围。
- SQLite 必需表、WAL、外键、迁移和最低种子数据。
- 1920×1080 ECharts 大屏布局、JSON 数据源和 30 秒刷新。
- RandomForest、特征、MAE/RMSE/MAPE、朴素基线、脚本模式和模型路径。
- 性能、尺寸、跨平台、文件行数、日志、安全、恢复和验收截图指标。

## 3. P0：必须先选择的交付策略

### Q1 是否采用 A/B 双路线

- A 线严格实现 SRS：Qt Widgets 双桌面程序 + SQLite 单机 + JSON 大屏 + Python ML。
- B 线实现此前规划：Android/QML + C++ 网络后端 + PostgreSQL + 云部署。
- 推荐：先交付 A 线，抽象领域和服务接口；A 线通过验收后再做 B 线。
- 不推荐：把所有技术直接混进一个首版，因为会同时增加验收偏差和开发风险。

### Q2 用户端 UI 技术

- SRS：Qt Widgets，固定 420×760，主要文件名为 `LoginWindow`、`StationListPage` 等。
- 扩展：Android 必须使用 Qt Quick/QML 才更适合移动端。
- 推荐：A 线保留 Widgets；B 线新增 QML，共享服务层而不是强行共享全部 UI。
- 待确认：是否允许 A 线改用 QML，只要在 Ubuntu 显示同等手机式界面。

### Q3 数据库与运行拓扑

- SRS：两个桌面进程直接共享 SQLite 文件，WAL 模式。
- 扩展：客户端只访问云后端，后端使用 PostgreSQL。
- 推荐：实现 `Repository` 接口及 SQLite/PostgreSQL 两个适配器；A 线禁止依赖云服务。
- 待确认：课程是否会检查 `charge_platform.db`、PRAGMA 和两个程序共享文件。

### Q4 Windows 构建是否必交

- SRS：Windows 10/11 可开发，NFR 要求 MSVC 2019 与 Ubuntu GCC 11 均可编译。
- 此前范围：只计划 Linux 管理端和 Android。
- 推荐：保留 Windows CI/构建兼容性，但以 Ubuntu 22.04 作为现场验收。
- 待确认：是否必须提交 Windows 可执行文件或只需证明可编译。

### Q5 Socket/pthread 与跨平台要求

- 原始要求书强调 Socket 和 pthread。
- SRS 基线采用共享 SQLite，没有功能性 Socket 用例，并禁止平台专有 API。
- B 线的 HTTPS/WebSocket 和 Qt 线程可以覆盖网络与并发训练目标。
- 待确认：验收是否要求直接展示 POSIX Socket/pthread 源码；若要求，需要单独的跨平台封装或演示模块。

## 4. P1：与既有决定冲突的产品规则

### Q6 登录与资料

| SRS 基线 | 既有决定 |
| --- | --- |
| 手机号必填且唯一 | 用户名必填、手机号选填 |
| 模拟验证码登录和自动注册 | 用户名/手机号 + 密码 |
| 默认昵称、头像，可修改 | 不需要昵称 |
| 新用户余额 0 | 新用户赠送 100 元 |

推荐：A 线严格按 SRS；B 线保留密码登录，并决定是否同步昵称、头像和赠送余额。

### Q7 预约与即时排队

- SRS：有空闲桩时直接预约，保留 15 分钟，超时取消。
- 既有决定：无空闲桩时即时排队，轮到后 5 分钟确认，不做未来预约。
- 两者可以兼容：直接预约是基础；无空闲桩时才进入扩展队列。用户在 5 分钟内确认分配后，再创建 15 分钟预约。
- 待确认：是否接受“两阶段倒计时”，以及队列按站点、类型还是具体设备建立。

### Q8 价格、余额与欠费

| SRS 基线 | 既有决定 |
| --- | --- |
| 每个站点一个单价 | 北京统一电费 + 服务费 |
| 金额保存在元、显示两位 | 推荐数据库保存整数分 |
| 余额不足扣至 0 并记欠费 | 达到余额上限自动结束，原则上不欠费 |
| 最低起充金额 5 元 | 目标金额 10/20/30 或自定义 |

推荐：A 线按站点总单价和欠费字段验收；B 线采用价格快照、费用拆分与余额自动停止。需要决定是否让两线共享同一个结算规则。

### Q9 数据规模和城市

- SRS：至少 5 站、每站 6～12 桩、每站 1～2 个故障桩、约 30 天订单。
- 既有决定：北京三个站、每站四桩，不模拟异常。
- 推荐：将北京扩展为至少 5 个站点，并生成满足 SRS 的设备与历史数据；故障桩仅用于管理演示。
- 待确认：是否接受增加两个北京站点，以及每站具体快慢充数量和功率。

### Q10 地图服务商

- SRS：腾讯地图可选，必须有预置坐标、Haversine 和系统浏览器兜底。
- 当前资源：已有高德 Key。
- 推荐：A 线实现腾讯链接与无 Key 降级；B 线可以在允许替换后接高德。
- 待确认：课程是否允许地图供应商等价替换。

### Q11 角色与权限

- SRS：车主、运营管理员、只读决策者。
- B 线：普通用户、运营人员、系统管理员。
- 推荐：A 线保留三种入口语义；B 线将运营权限细分，决策者对应只读大屏权限。
- 待确认：A 线大屏是否需要登录；SRS 未要求。

## 5. P2：SRS 内部仍不完整或有矛盾的业务问题

1. 模拟验证码有效期、最大错误次数和重新获取后的旧码失效规则未定义；建议 10 分钟、最多 5 次、获取新码后旧码立即失效。
2. UC-U-06 要求充电中订单跳“结算页”，NFR-R-01 又要求恢复继续计费；需定义该页面是继续充电控制还是立即结束结算。
3. BR-04 写“余额大于最低起充金额”，是严格 `>` 还是 `>= 5.00`？建议使用 `>=`。
4. BR-06 允许欠费，但未定义欠费字段、还款方式和再次充电限制。
5. 管理员重启使用中设备会中断充电，但订单的结束时间、费用、状态和余额处理未定义。
6. 冻结正在充电的用户后，当前充电是否继续、是否允许结算和充值未定义。
7. 修改站点单价是否影响已预约或正在充电订单；建议预约时保存价格快照。
8. 删除电桩仅禁止“使用中”，但存在历史订单或预约时是否允许删除未定义；建议逻辑停用。
9. 预约订单和充电订单共用 `charging_order`，状态码以后增加排队、待支付、失败时如何兼容未定义。
10. 时间以本地字符串保存时，格式、时区和夏令时行为未定义；建议固定 ISO 8601 格式。
11. 头像复制失败、同名覆盖、图片解码失败和注销后的文件清理未定义。
12. 充值流水虽然标为可选，但余额审计和异常恢复需要它；建议提升为必做。

## 6. P3：数据、大屏和 ML 的实现细节

### 数据库

- 确定所有表字段、类型、约束、索引和外键删除行为。
- 明确金额采用整数分、定点数还是 SQLite REAL，并设计迁移到 PostgreSQL 的映射。
- 明确两个进程同时写 SQLite 时的 busy timeout、重试上限和用户提示。
- 确定种子数据生成是否固定随机种子，以及是否每次可重建相同演示数据。
- 定义数据库损坏检测、备份和恢复步骤。

### Dashboard JSON

- 谁负责每 30 秒导出：管理端常驻任务、独立脚本还是手动刷新？
- 使用临时文件 + 原子替换，防止浏览器读取半个 JSON。
- 定义 schema 版本、生成时间、空值和无数据表示。
- B 线切换 API 后是否仍保留 JSON 离线演示模式。

### 机器学习

- 明确训练集至少覆盖多少天；30 天不足以稳定生成 168 小时滞后特征时如何处理。
- 节假日与模拟天气如何生成并保证可复现。
- 训练/验证/测试按时间切分，禁止随机打乱导致数据泄漏。
- MAPE 遇到真实值 0 时的计算方式。
- “必须优于基线”如果未达到，验收是报告事实、调参重训还是阻止发布。
- 预测空闲桩数和高峰标记的计算公式、上下界和阈值。
- QProcess 超时、并发点击、脚本崩溃、模型缺失和旧结果保留策略。
- `.pkl` 模型只加载本项目自己生成的可信文件，不接受用户上传。

## 7. P4：非功能与验收信息缺口

- 性能测试使用何种硬件、数据集、冷/热缓存和重复次数。
- CPU <5% 的测量工具、采样窗口和机器基准。
- “单文件不超过 400 行”是否包含 UI 自动生成文件、测试和脚本。
- 日志保留期、最大文件大小、轮转和敏感字段脱敏。
- 管理员加盐 SHA-256 的盐长度、迭代方式和未来迁移策略；B 线应采用专用密码哈希。
- Ubuntu 22.04 验收机器是否已安装 WebEngine、Charts、Python 和 Node 依赖。
- 截图命名、演示数据固定性、现场演示时长和评分权重。
- 是否还需要总体设计、详细设计、数据库设计、测试报告和发布说明。

## 8. 推荐扩展路线

完成 A 线后按风险由低到高扩展：

1. 将 SQLite 访问封装成仓储接口，补充单元和事务测试。
2. 增加即时排队，复用预约与设备占用规则。
3. 增加 Android QML 客户端，共享领域 DTO 和服务接口。
4. 增加 C++/Qt 网络后端，将客户端数据访问替换为 HTTPS/WebSocket。
5. 增加 PostgreSQL 适配器、迁移、云部署、Nginx/TLS 和备份。
6. 增加 TPNS、刷新令牌、细粒度角色、审计与安全登录。
7. 大屏从 JSON 轮询升级为 API/WebSocket，同时保留离线模式。
8. ML 从随机森林扩展到 LightGBM/LSTM，再考虑故障诊断和调度优化。
