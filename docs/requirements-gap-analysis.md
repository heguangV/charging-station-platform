# 单一目标的需求决策与未确定问题

## 1. 已统一的最终方向

项目最终只建设一套由 Android/Linux 用户端、Linux 管理端、C++/Qt 后端、PostgreSQL、Web 大屏和 Python ML 组成的系统。

SRS 的功能、异常流和可观测结果保留；技术替换必须能够显著改善移动端支持、并发、云部署或安全性。

## 2. 已确定的等价增强

| 事项 | 单一目标决定 |
| --- | --- |
| 用户端 UI | Qt Quick/QML，同时构建 Android 和 Linux 手机式窗口 |
| 管理端 UI | Linux Qt Widgets + Qt Charts |
| 数据访问 | 客户端只访问 C++/Qt HTTPS/WebSocket 服务 |
| 数据库 | PostgreSQL，不再建设 SQLite 主版本 |
| 金额 | 数据库存整数分，界面/API 显示元和两位小数 |
| 时间 | 服务端保存 UTC，客户端显示本地时间 |
| 密码 | 使用专用密码哈希，不使用单次加盐 SHA-256 |
| 大屏 | API/WebSocket 为主，保留原子 JSON 导出降级 |
| Socket/线程 | 使用 Qt 跨平台封装，不直接依赖 pthread/POSIX 专有 API |
| 地图 | 按 SRS 使用腾讯地图，并保留预置坐标/Haversine/浏览器降级 |
| ML | 按 SRS 使用 RandomForest、规定特征与三种评估指标 |

## 3. 已合并的产品规则

- SRS 的直接预约与既有即时排队同时存在：有空闲桩直接预约 15 分钟；无空闲桩加入队列，轮到后 5 分钟确认，再进入 15 分钟预约。
- 保留用户名/手机号 + 密码作为正式登录；开发环境额外提供 SRS 模拟验证码自动注册演示。
- 恢复 SRS 的昵称、头像和手机号必填要求；新用户初始余额按 SRS 设置为 0。
- 每站保存电费和服务费，总价等价于 SRS 的站点单价；北京种子数据默认统一价格。
- 正常充电达到余额上限自动停止；发生不可避免的计费超额时记录欠费，兼容 SRS 兜底。
- 北京站点扩展至至少 5 个，每站 6～12 个桩，保留故障设备和约 30 天历史数据。
- 三角色统一为车主用户、运营管理员、决策查看者。
- 大屏、云服务、Android、推送和 ML 都属于同一个最终目标。

## 4. P0：需要用户确认的核心规则

### Q1 排队建立范围

即时队列按以下哪种维度建立：

- 推荐：`站点 + 快充/慢充类型`。系统分配该类型最先空闲的设备。
- 备选：整个站点统一队列，可能分配用户不想使用的功率类型。
- 不推荐：指定具体设备排队，容易造成其他设备闲置。

### Q2 价格管理范围

- 当前整合：每站保存电费和服务费，北京种子数据初始值相同。
- 需要确认：管理员修改价格时，是全市统一批量修改，还是允许单独修改某站。
- 推荐：支持单站修改，同时提供“一键同步全市价格”。

### Q3 欠费后的账号行为

- 当前整合：正常情况下余额上限自动停止；极小计费超额记录欠费。
- 需要确认：欠费用户是否禁止登录、只禁止新充电，还是充值后自动清偿。
- 推荐：允许登录和充值，禁止新预约/排队；充值优先清偿欠费。

### Q4 使用中设备远程重启

- SRS 允许二次确认后重启使用中设备，但没有定义订单如何结束。
- 当前安全默认：使用中设备禁止远程重启。
- 如果必须允许，需要明确强制结束、费用结算、用户通知和审计流程。

### Q5 决策查看者登录

- 需要确定大屏是公开只读、独立查看者账号登录，还是运营管理员登录后访问。
- 推荐：独立只读账号；公网不允许匿名访问运营数据。

## 5. P1：状态机和业务细节

1. 排队取消后是否立即递补下一位；建议是。
2. 5 分钟确认和 15 分钟预约期间，用户是否允许主动取消；建议允许并立即释放。
3. 管理员是否能强制释放待确认/预约设备；建议仅运营管理员可操作并填写原因。
4. 订单状态需要覆盖排队、待确认、已预约、充电中、待结算、已完成、已取消、结算失败；具体编码尚未冻结。
5. 价格修改不应影响已预约或充电中的订单，建议分配/预约时保存价格快照。
6. 冻结正在充电的用户时，当前会话继续，用户仍可结束和结算，但不能创建新流程。
7. 设备、站点和用户存在历史订单时使用逻辑停用，不物理删除。
8. 网络中断后由后端继续计费；客户端恢复后是进入充电控制页还是待结算页，由服务器状态决定。
9. 模拟验证码默认 10 分钟和 5 次尝试是否接受。
10. 用户注销后的头像文件、预测相关行为数据和审计记录保留期限尚未确定。

## 6. P2：站点、设备和演示数据

需要确定：

- 至少 5 个北京站点的名称、地址、经纬度和站点缩写。
- 每站快充/慢充数量、功率、接口类型和初始故障设备。
- 统一初始电费、服务费和最低起充金额。
- 设备编号规则；建议 `站点缩写-类型-两位序号`。
- 30 天历史订单的每日数量、时段分布、充值和用户规模。
- 注册用户、同时在线、并发排队和并发充电的目标数量。

## 7. P3：数据库、API 与安全设计

- 冻结 PostgreSQL 主版本、数据库名、服务账号和迁移命名规则。
- 定义所有金额、定点电量、UTC 时间和状态枚举的数据库类型。
- 定义并发分配设备的锁策略和事务隔离级别。
- 定义 REST 资源、错误码、幂等键、分页和 WebSocket 事件协议。
- 确定访问令牌/刷新令牌有效期、设备解绑和同时登录策略。
- 确定头像存储目录、访问 URL、文件扫描和清理机制。
- 确定日志轮转、数据保留、备份目录、恢复目标和磁盘告警。
- 确定腾讯地图 Key 的应用限制和服务器代理范围。
- 确定 TPNS 套餐、Token 绑定、通知权限和失败重试策略。

## 8. P4：大屏与机器学习细节

### 大屏

- 决定 WebSocket 推送频率和30秒轮询的具体降级条件。
- 定义 Dashboard API/JSON schema、版本和空值规则。
- 确定指标口径、截止时间和时区。
- 确定生产大屏的鉴权、会话时长和只读账号管理。

### 机器学习

- 30 天数据无法完整提供稳定的 168 小时滞后样本时，建议生成至少 90 天训练数据，但界面默认展示近 30 天。
- 天气和节假日数据生成方式、随机种子和缺失值处理尚未冻结。
- 数据必须按时间切分，MAPE 遇到真实值 0 时需要定义计算方式。
- “必须优于朴素基线”未达到时，是阻止发布还是展示真实结果并继续调参，需要确定。
- 预测空闲桩和高峰标记的公式、边界和阈值尚未确定。
- ML 任务超时、并发运行、模型缺失和上次结果保留时长需要定义。

## 9. P5：部署、界面与交付信息

- 云服务器 CPU 架构、CPU、内存、磁盘和开放端口。
- 公网 IP 阶段 TLS 方案以及域名申请时间。
- Android 最低版本、应用显示名称和是否只支持竖屏。
- Linux 用户端、管理端和大屏的最终视觉风格与 Logo。
- 是否要求 Windows 构建产物，还是只维持源码可编译性。
- 项目截止时间、演示时长、测试报告和设计文档清单。
- 团队成员、分工、Pull Request 审核人数和 GitHub Actions 矩阵。
