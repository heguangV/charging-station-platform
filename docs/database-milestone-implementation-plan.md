## 0. 前置条件（步骤 0）

1. 当前工作区未提交的增强任务改动（`UC-U-11`/`UC-X-01` 的 SRS V1.1、指南阶段八、追踪矩阵重构、`enhancement-tasks-implementation-plan.md`、`apps/user/net` 改动等）必须先提交或暂存，形成稳定基线 `BASE`。**六条工作流全部从 `BASE` 拉分支**——SQLite 实现（PR #8）与 `b17ad18`（迁移并发测试）只存在于 `codex/tencent-navigation-integration`，`main` 无数据库实现。
2. 分支命名遵循指南 §7.1：`feature/dust/<主题>`；主题为小写英文连字符。远期并入 `develop` 的路线由集成时决定，不在本计划内扩展。
3. 将本文档登记进 `development-guide.md` §1 文档职责表（与步骤 0 的提交同批）。

## 1. 共同实施原则（指南 §5~§8 摘录，逐条适用）

- 抄录 SRS 验收标准，不在任务中重新解释需求（§5.1）。
- 数据库迁移、公开路由、错误码变更：先更新对应设计文档与契约测试，再改代码（§7.2.4）；需求变化先改 SRS（§7.2.5）。
- 测试先行：先增加领域/数据库/契约测试，再实现（§5.3）。
- 测试数据库、日志、模型和截图使用隔离目录，不得污染开发或演示数据（§6）。
- 每个提交只表达一个目的，标题用 `feat:`/`fix:`/`docs:`/`test:` 前缀（§7.2.2）；提交前跑 `scripts/check.sh` 与 `git diff --check`（§8）。
- 新源文件遵守 NFR-M-01 单文件 ≤ 700 行；`sqlite_repository.cpp` 为存量豁免文件。
- 完成定义（§8）：可追踪 SRS 编号、正常流/异常流/权限/边界有测试证据、符合设计文档约束、构建与测试通过、文档与追踪关系已同步。

## 3. W1：UC-D-02 完整演示种子（任务 #2）

**抄录验收标准（SRS UC-D-02）**：首启无库时在初始化锁保护下自动建表并播种，已存在库按 `schema_version` 升级，失败时拒绝写入并通过健康检查返回明确状态；种子为 1 管理员 + 5 固定北京站点 + 48 电桩 + 最近 90 天订单/充值/设备状态/负荷数据；不重复播种、已执行迁移不得修改、`INSERT OR IGNORE` 幂等。固定站点表（ZGC/CYGY/BJN/SJS/TZYH 及坐标）、设备表（120kW/60kW/7kW 数量与 6 台初始故障设备编号）、五区价格表、全市最低起充 500 分、调价只作用于服务费；历史种子固定随机种子 `20260901`：300 用户、约 9,000 订单、约 900 充值、日订单 80~120、94% 完成/6% 取消、无结算失败、70/30 快慢充、工作日与周末高峰时段、五站占比 28/24/22/14/12%、小时级补零保证序列连续。

**设计决策（实现前确定，记入 database-design.md）**：

1. **形态**：作为**新迁移 v8** 与结构迁移同机制（`schema_version` 守卫 + `INSERT OR IGNORE` 幂等），种子 SQL 放独立 `sqlite_seed.cpp`，`initialize()` 调用。不修改 v1~v7。
2. **时间锚点**：90 天历史锚定在 v8 **首次执行时刻**（SRS 只要求首启/首升时"最近 90 天"，且"已存在数据库时不重复播种"禁止滚动刷新）。小时级负荷不直接播种，由既有 `refreshHourlyMetrics` 从订单聚合重建并补零。
3. **与 v1 临时种子协调**：v1 已播种 ZGC（5 桩）、XEQ、CBD 与两区价格。v8 按稳定编码 `INSERT OR IGNORE` 补齐 5 站/48 桩/5 区价格、按固定表修正 6 台故障桩状态；XEQ/CBD 不在 SRS 固定清单内，**仅当无业务引用时删除**（含其电桩），有引用则保留并在文档记录偏差。

**实施步骤**：① 数据库测试先行（种子完整性/幂等重跑/升级后数据保留）→ ② v8 + `sqlite_seed` 实现 → ③ 全量验证 → ④ 更新 database-design.md。

**退出门禁**：5 站 48 桩逐站数量与故障编号断言、五区价格断言、300/9000/900 规模断言、94%/6% 与 70/30 占比断言、五站订单占比断言、高峰时段分布断言、小时序列无空洞；重复初始化不重复；已有库升级后业务数据保留且重放幂等。

## 4. W2：数据保留清理测试（任务 #3）

**抄录验收标准**：NFR-M-04 "应用日志保留 30 天，审计/运维日志保留 180 天"；UC-M-04 "模型保留 30 天，预测和评估历史保留 90 天；失败保留最近成功结果并标记过期"。

**现状**：`cleanupAdminRecords`（ops_log/device_command 180 天、outbox 已投递 7 天/死信 30 天、备份轮换）与 `cleanupAnalytics`（load_prediction 90 天、model_version 30 天且保留被引用模型、小时指标 365 天）已实现并挂进维护任务，但**零测试覆盖**（现有测试只覆盖备份与 outbox）。

**实施步骤**：① 在 `tests/sqlite_repository_test.cpp` 追加保留清理测试块 → ② 矩阵行修正随 §9 统一收尾。

**退出门禁**：180 天边界（179/181 天）断言；引用完整性（被 load_prediction 引用的 model_version 不得删除）；pending/近期行保留；清理前后业务数据无损。

## 5. W3：损坏库错误路径测试（任务 #4）

**抄录验收标准（NFR-R-02）**："SQLite 打开失败、文件损坏、版本不匹配、锁超时或事务失败时给出明确提示而非崩溃或静默丢数据"。

**现状**：打开失败抛 `"database unavailable: ..."`、`busy_timeout` 5000ms、校验和不匹配拒绝写入，前两者已有测试；缺**文件损坏**路径——SQLite 对损坏文件常打开成功、首次读页才报 `SQLITE_CORRUPT`/`SQLITE_NOTADB`。

**实施步骤**：① 新建 `tests/sqlite_corruption_test.cpp`：非 SQLite 文件、页翻转、截断三种损坏 → 断言明确报错（异常/就绪状态 `check()` 失败）而非崩溃或静默丢数据 → ② 注册 target。

**退出门禁**：三种损坏场景均有断言；已有打开失败/锁等待测试保持通过。

## 6. W4：真实管理员账号管理（任务 #5）

**需求缺口**：SRS 只规定 `admin/123456` 演示登录（UC-A-01），无创建真实管理员、修改密码的用例；当前只有演示种子 `ensureDevelopmentAdmin`。按指南 §7.2.5，**先改 SRS 再改设计、代码和测试**。

**实施步骤**（顺序不可调换）：

1. SRS §4 追加 `UC-A-09 管理员账号管理`（OWNER 创建/停用管理员、本人修改密码；沿用 UC-A-01 的锁定与口令哈希规则）。
2. `docs/database-api.md` 追加端点契约（如 `POST /api/v1/admin/accounts`、`PUT /api/v1/admin/accounts/{id}/status`、`PUT /api/v1/admin/me/password`）与错误码。
3. 契约测试先行（`ncs_admin_routes` 模式）。
4. 仓储接口 + 内存实现 + `sqlite_repository` 方法区实现（`admin_account` 表已存在，无 schema 迁移）。
5. `admin_routes.cpp` 接入，跑集成与烟雾测试。

**退出门禁**：SRS/接口文档/契约测试/实现四方一致；非 OWNER 越权被拒；新密码强制下次改密标志与登录锁定协同；`admin/123456` 演示登录不受影响。

## 7. W5：NFR-P-02 营收聚合微基准（任务 #6，依赖 W1）

**抄录验收标准（NFR-P-02）**："营收图表（30 天聚合）查询 < 300ms"。

**并行安排**：基准骨架（`tests/sqlite_revenue_bench.cpp`，非功能测试层）可与 W1 并行开发，用合成数据跑通测法；**正式数字在 W1 合并后**用 90 天种子数据在隔离库上输出。

**退出门禁**：NFR-D-01 口径（2 核/4GB VM）下 30 天聚合查询多次运行 < 300ms，输出可重复证据（中位数与最差记录）；文档记录测量方法与结果。

## 8. W6：NFR-P-04/05 容量与吞吐端到端压测（任务 #7）

**抄录验收标准（NFR-P-04/05 + SRS §8 末段）**：3,000 注册账号、100 个同时在线连接、50 个同时排队流程、48 个同时充电会话；HTTPS API 持续 20 请求/秒并承受 50 请求/秒短时峰值，WebSocket 100 个在线会话。"容量与并发测试不得依赖真实用户。测试环境使用独立 SQLite 文件和仅在测试配置启用的模拟账号，由 Python `asyncio` HTTP/WebSocket 虚拟客户端连接 Crow 服务……测试环境禁用外部通知；测试结束后删除并重建测试库，不把测试账号或固定密码用于正式演示。"

**实施步骤**：① `tests/performance/`（新目录，Python，参照 `server_smoke_test.py`）编写虚拟客户端与数据准备（注册 API 生成 3,000 账号、管理 API 建桩、演示管理员仅用于测试库）→ ② 独立测试库上执行容量与吞吐场景 → ③ 记录证据，矩阵行随 §9 同步。

**退出门禁**：NFR-P-04 三个容量数字全部达标；NFR-P-05 持续/峰值吞吐达标且错误率可接受；测试库结束后删除重建；全程不触真实用户数据。

## 9. 集成与收尾

1. **合并顺序**：W1 最先合并（W5 依赖其种子）；W2/W3/W4/W6 任意序；冲突按 §2 归属表机械解决。
2. **矩阵统一同步**（一次 `docs:` 提交）：UC-D-02 行转完成、NFR-M-04 行改为"已实现已测"、NFR-R-02 行转完成、NFR-P 行给出证据链接、新增 UC-A-09 行。
3. **整体门禁**（阶段七口径）：全部数据库/契约/集成测试、`scripts/check.sh`、`git diff --check`、服务端烟雾测试通过；追踪矩阵无未验证条目。

## 10. PR 要求（指南 §7.3 摘要）

每条工作流一个 PR：关联需求编号、背景与不包含范围、受影响模块/数据/接口、实际构建与测试结果、迁移与部署说明（W1、W4 适用）、回滚方式。PR 聚焦一个可验证目标，合并前至少一名成员批准。
