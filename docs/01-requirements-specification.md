## 1. 引言

### 1.1 编写目的

本文档定义充电桩应用管理平台的全部功能需求与非功能需求，作为三类读者的共同依据：

- **学生（）**：明确每个模块要做什么、做到什么程度算完成。
- **AI 代码生成工具**：作为长期上下文源，避免每次对话重述需求导致 token 浪费和理解漂移。
- **实训验收方**：逐条对照验收标准检查交付物。

### 1.2 术语与缩写

| 术语           | 说明                             |
| ------------ | ------------------------------ |
| 电站 / Station | 一个物理充电站点，含地址与经纬度，下挂多个电桩        |
| 电桩 / Charger | 一个具体充电设备，属于某个电站，有类型、功率、状态      |
| 活动流程 / Flow | 一次排队、报价、预约、充电和结算状态链             |
| 订单 / Order   | 一次已确认预约或充电行为的业务凭证                 |
| 免密登录         | 仅凭手机号登录，手机号不存在时自动注册            |
| 活动流程         | `status` 为 10、20、30、40、50 或 80 的未完成/待恢复流程；60、70、90 为终态 |
| Haversine    | 球面两点距离公式，用于本地计算用户与电站的直线距离      |
| SoC          | State of Charge，电池荷电状态，本项目用模拟值 |

### 1.3 需求编号规则

```
UC-<子系统>-<序号>      用例（功能需求）
NFR-<类别>-<序号>       非功能需求

```

子系统代号：`U` 用户端、`A` 管理端、`D` 数据库端、`W` Web 大屏、`M` 机器学习。

## 2. 总体描述

### 2.1 系统定位

平台覆盖 **用户服务 → 设备运维 → 数据存储 → 决策分析 → 智能预测** 全链条，由五个子系统构成：

| 子系统          | 形态               | 技术                     | 优先级  |
| ------------ | ---------------- | ---------------------- | ---- |
| 充电用户端        | Linux 桌面手机式竖屏窗口 | Qt Widgets + C++       | P0   |
| PC 管理端       | 宽屏管理 GUI     | Qt Widgets + Qt Charts + Qt Network | P0   |
| 业务服务端       | 独立 HTTPS REST/WebSocket 服务 | Crow + C++17 | P0   |
| 数据库端         | 单文件数据库           | SQLite 3               | P0   |
| 大数据可视化大屏     | Web 页面           | Vue 3 + ECharts        | P1   |
| 机器学习智能分析     | 离线脚本 + 结果回写      | Python + scikit-learn  | P1   |

### 2.2 用户角色

| 角色    | 描述                    | 入口                |
| ----- | --------------------- | ----------------- |
| 车主用户  | 电动汽车车主，查站、导航、充电、充值    | `ncs_user` 可执行程序  |
| 运营管理员 | 平台运维人员，监控设备、分析营收、管理用户并查看运营大屏 | `ncs_admin` 可执行程序和浏览器大屏 |
| 决策查看者 | 只读查看运营大屏和预测信息，不执行管理操作 | 浏览器大屏 |

### 2.3 运行环境假设

- `ncs_user`、`ncs_admin` 与 `ncs_server` 在同一 Ubuntu 环境运行；客户端通过 `/api/v1` HTTPS REST 和鉴权 WebSocket 访问业务。
- `ncs_server` 作为唯一可信业务与数据边界，承载鉴权、事务、设备模拟、持续计费、排队调度、到期处理与实时通知；只有该进程可打开 SQLite。
- 开发、测试数据库使用不同 SQLite 文件。VM 在校园网环境固定使用 NAT；跨机器部署属于远期路线，不通过网络共享 SQLite 文件。
- 无真实 GPS 硬件，用户位置由界面选择区域或输入地址后**软件模拟**。
- 无真实充电桩硬件，充电过程由定时器按功率模拟累积电量。
- 腾讯地图为可选外部依赖：有网络且配置了 Key 时用真实地图，否则退化为本地 Haversine 距离计算 + 系统浏览器打开地图链接。

### 2.4 业务规则（全局约束）

| 编号    | 规则                                       |
| ----- | ---------------------------------------- |
| BR-01 | 手机号是用户唯一标识，必须为 11 位数字且以 1 开头             |
| BR-02 | 一个用户同一时刻最多只能有一个未结算订单                     |
| BR-03 | 一个电桩同一时刻最多只能被一个订单占用                      |
| BR-04 | 预约和开始充电前用户余额必须不少于全市统一最低起充金额 5.00 元         |
| BR-05 | 充电费用 = 累计电量 ×（电费快照 + 服务费快照），结算按分计算并显示两位小数 |
| BR-06 | 结算时从用户余额扣款，余额不足则扣至 0 并记录欠费金额             |
| BR-07 | 被冻结（`status=0`）的用户不能登录，不能开始新的充电          |
| BR-08 | 故障（`status=2`）的电桩不可被预约或开始充电              |
| BR-09 | SQLite 中金额使用整数分、电量使用整数毫瓦时、时间使用 UTC Unix 秒时间戳；界面按元、kWh 和本地时间展示，保持说明书可观察语义 |
| BR-10 | 电站和电桩不物理删除；电站通过启用/停用接口管理，电桩通过状态接口置为停用；存在活动流程时禁止停用并提示，历史数据必须保留 |
| BR-11 | 仅运营管理员可二次确认后强制释放待确认或已预约设备，必须填写原因、选择设备后续状态、通知用户并审计；充电中设备不得直接强制释放，但可按 UC-A-05 的受控中断、结算和审计流程执行紧急远程重启 |
| BR-12 | 活动流程状态码固定为 10 排队、20 待报价确认、30 已预约、40 充电中、50 结算中、60 已完成、70 已取消、80 结算失败、90 已过期 |

## 3. 充电用户端需求（UC-U）

### UC-U-01 手机号免密登录 / 自动注册

**角色**：车主用户
**前置条件**：程序启动，Crow 服务端可连接。

**主流程**

1. 显示登录窗口，含手机号输入框、"获取验证码"按钮（模拟，点击后按钮进入 60 秒倒计时）、验证码输入框、"登录/注册"按钮。
2. 用户输入 11 位手机号，点击"获取验证码"，系统生成 6 位随机码并直接在界面提示区显示（模拟短信下发）。
3. 用户输入验证码，点击登录。
4. Crow 服务端校验验证码一致后，按手机号查询用户。
5. 手机号存在且 `status=1` → 登录成功，加载用户信息进入主窗口。
6. 手机号不存在 → 服务端在事务内创建用户和钱包，昵称默认 `用户` + 手机号后 4 位，头像为空（界面显示默认灰色头像），余额 0，状态正常，随后登录成功。

模拟验证码有效 10 分钟、最多错误 5 次，60 秒内不能重复获取；生成新码后旧码立即失效。验证码只在当前本地开发界面显示，不写入日志。

短信免密登录是默认且必须验收的入口。用户也可使用短信验证码注册用户名和密码、在用户中心设置或修改凭据，并使用用户名或完整手机号进行密码登录；可查看并撤销自己的其他登录会话。密码登录不得替代或削弱短信免密登录和自动注册流程。

**异常流**

| 编号   | 条件         | 系统响应                      |
| ---- | ---------- | ------------------------- |
| E1   | 手机号格式不合法   | 提示"请输入正确的 11 位手机号"，不查询数据库 |
| E2   | 未获取验证码直接登录 | 提示"请先获取验证码"               |
| E3   | 验证码错误      | 提示"验证码错误"，允许重试            |
| E4   | 用户已被冻结     | 提示"账号已被冻结，请联系客服"，拒绝登录     |
| E5   | 服务端或数据服务不可用 | 显示不泄露内部路径、SQL 或堆栈的明确提示，并允许重试或退出程序 |

**验收标准**

- 新手机号首次登录后，`user_account` 表新增一条记录，昵称符合默认规则。
- 同一手机号第二次登录不再新增记录，且能带出上次修改过的昵称和余额。
- 管理端把该用户冻结后，用户端再次登录被拒绝。

### UC-U-02 附近充电站查询

**前置条件**：用户已登录。

**主流程**

1. 主窗口默认进入电站列表页。
2. 页面顶部提供定位区：区域下拉框（预置若干城市/城区）+ 地址输入框 + "定位"按钮。
3. 用户选择区域或输入地址后点击定位：
   - 若已配置腾讯地图 Key 且网络可用 → 调用地理编码接口把地址转为经纬度。
   - 否则 → 使用区域下拉框对应的预置经纬度作为当前位置。
4. 系统读取全部电站，用 Haversine 公式计算每个电站与当前位置的距离，按距离升序排列。
5. 列表以卡片形式展示每个电站：站名、单价（元/度）、`空闲数/总桩数`、距离（公里，保留 1 位小数）。
6. 卡片上的空闲数量根据 `charger` 表实时统计（`status=0` 计为空闲）。

**异常流**

| 编号   | 条件          | 系统响应                       |
| ---- | ----------- | -------------------------- |
| E1   | 地址解析失败或网络超时 | 提示"地址解析失败，已使用默认位置"，退化为预置坐标 |
| E2   | 电站表为空       | 列表区显示占位文案"暂无充电站数据"         |

**验收标准**

- 切换不同区域后列表顺序随之变化，距离数值合理（同城应在几公里到几十公里量级）。
- 管理端把某个电桩状态改为使用中后，用户端刷新，对应电站空闲数减 1。

### UC-U-03 电站详情与电桩列表

**主流程**

1. 用户点击电站卡片，进入电站详情页。
2. 顶部显示电站名称、详细地址、单价、距离。
3. 中部以表格展示该站所有电桩：编号、类型（快充/慢充）、功率(kW)、状态（空闲/使用中/故障）、累计充电次数。
4. 状态列用不同颜色文字区分：空闲绿色、使用中橙色、故障红色。
5. 底部提供"一键导航"和"选桩充电"两个按钮。

**验收标准**：表格行数与该电站 `charger` 记录数一致；状态文字与数据库值对应正确。

### UC-U-04 一键导航

**主流程**

1. 用户在电站列表点击距离信息，或在详情页点击"一键导航"。
2. 打开导航页，页面顶部提供出行方式选择：驾车 / 步行 / 公交。
3. 页面主体为地图区域：
   - **方案 A（已装 Qt WebEngine 且配置了 Key）**：`QWebEngineView` 加载本地 HTML 模板，模板内用腾讯地图 JS API 渲染地图并绘制起点到终点的路线。
   - **方案 B（兜底）**：显示起终点坐标与直线距离信息卡，提供"在系统浏览器中打开"按钮，用 `QDesktopServices::openUrl` 打开腾讯地图路线规划 URL。
4. 起点为当前定位位置，终点为目标电站经纬度。

**异常流**：网络不可用时页面显示明确提示，不崩溃、不空白假死。

**验收标准**：能截图到地图路线规划画面（方案 A 内嵌截图，方案 B 浏览器截图）。

### UC-U-05 用户中心与信息维护

**主流程**

1. 底部导航点击"我的"进入用户中心。
2. 展示：头像（圆形，未设置时显示默认灰色头像）、昵称、手机号（中间 4 位打码）、钱包余额、注册时间。
3. **更换头像**：点击头像 → 文件选择对话框（限 `*.png *.jpg *.jpeg *.bmp`）→ 客户端先校验格式和大小并上传 → Crow 服务端再次校验真实格式、大小和尺寸，重新编码并剥离元数据后保存到服务端文件目录 → 返回受权 `avatarUrl` → 界面立即刷新。客户端不得保存服务端文件路径或直接写 SQLite。
4. **修改昵称**：点击编辑 → 输入框可编辑 → 通过 REST 接口保存并刷新。昵称长度 1-20 字符，不允许纯空白。
5. **余额充值**：输入金额（0.01 - 10000，两位小数）→ 点击充值 → 通过幂等 REST 接口完成虚拟支付 → 余额累加并生成充值流水 → 界面显示"支付成功"并刷新余额。
6. **退出登录**：返回登录窗口，清空当前会话。
7. **申请注销**：撤销全部令牌并删除登录凭据，立即匿名化用户名和手机号；头像在 24 小时内删除，匿名订单/钱包/充电记录保留 3 年，审计/运维日志保留 180 天，匿名 ML 聚合数据保留 1 年。

**异常流**

| 编号   | 条件                 | 系统响应                   |
| ---- | ------------------ | ---------------------- |
| E1   | 选择的图片文件过大（> 5MB）   | 提示"图片过大，请选择 5MB 以内的图片" |
| E2   | 充值金额非法（非数字、≤0、超上限） | 输入框标红并提示合法范围，不写库       |
| E3   | 昵称为空或全空格           | 提示"昵称不能为空"，保留原值        |

**验收标准**：修改昵称、头像、余额后重启程序仍然保留；充值 100 元后余额精确增加 100.00。

### UC-U-06 充电前未结算订单拦截

**前置条件**：用户已登录，点击"充电"入口。

**主流程**

1. 进入充电页面前，客户端调用 `GET /api/v1/user/flows/active`；服务端按 `charging_flow.status IN (10,20,30,40,50,80)` 查询当前用户的未完成或待恢复流程。
2. **存在** → 不允许创建新流程，并按状态恢复对应页面：10 返回排队页，20 返回报价确认页，30 返回预约页，40 返回充电页，50 或 80 返回结算/重试页。处于 40、50 或 80 时提示"您有未完成的充电订单，请先结算"。
3. **不存在** → 正常进入选桩页面。

**验收标准**：制造一条充电中流程后，反复点击充电入口都会恢复到该流程的充电页且不能创建新流程；制造结算中或结算失败流程时恢复到结算/重试页。

### UC-U-07 选桩、预约与开始充电

**主流程**

1. 选桩页展示当前电站的空闲电桩（仅 `status=0`），显示编号、类型、功率；用户可指定 `preferredChargerId`，未指定时由服务端按站点和类型分配。
2. 用户提交充电请求后，服务端校验余额、欠费、账号及活动流程唯一性：有兼容空闲设备时占用设备并进入 `status=20`（待报价确认），没有设备时进入按“站点+类型”的 FIFO 队列 `status=10`。
3. 设备可用后服务端生成带价格快照的报价并开始 5 分钟倒计时；指定设备在分配前已不可用时返回并发冲突，客户端刷新列表后重新选择。
4. 用户确认有效报价后，服务端在事务内创建订单，将 `charging_flow.status` 置为 30（已预约），进入充电控制页并开始 15 分钟预约保留倒计时。
5. 用户点击"开始充电"：服务端再次校验余额、预约归属、预约期限和设备状态，将 `charging_flow.status` 置为 40（充电中），写入 `start_time` 并启动持续计费。
6. 用户可在排队等待、5 分钟报价确认或 15 分钟预约阶段主动取消；系统在事务内使活动流程进入取消终态、使报价失效、释放设备并立即递补下一位，不收取费用。
7. 充电开始后不再允许取消，只能结束充电并按实际电量结算。取消接口必须幂等，重复请求不得重复释放设备或生成重复记录；第一版不设置取消处罚，但保存取消阶段、原因和服务端时间。
8. 运营管理员强制释放待确认或已预约设备时，当前流程转为已取消，用户不自动重新排队但通知提供重新排队入口；系统按管理员选择把设备置为空闲、故障或停用。该操作不收费，充电中设备拒绝执行。

**异常流**

| 编号   | 条件           | 系统响应                           |
| ---- | ------------ | ------------------------------ |

### UC-U-09 结束充电与订单结算

## 7. 机器学习子系统需求（UC-M）

### UC-M-01 数据准备

从 `charging_order` 导出训练集，按 `(电站, 日期, 小时)` 聚合，特征包括：小时、星期、是否周末、是否节假日、近 1/24/168 小时滞后负荷、滑动均值、电站编码、模拟天气（温度、是否降水）。标签为该小时充电量（度）。

模拟天气使用随机种子 `20260901`，节假日使用仓库内版本化日历；数值缺失使用训练集中位数，分类缺失记 `UNKNOWN`，不足 168 小时滞后的起始样本不参加训练。

### UC-M-02 模型

- 第一版：`RandomForestRegressor`（scikit-learn），可解释、训练快、无需 GPU。
- 评估指标：MAE、RMSE、MAPE，并与"用上周同一时刻值作为预测"的朴素基线对比。MAPE 只计算真实值大于 0 的样本并报告排除数量，同时提供 WAPE。
- 模型必须在固定测试集上优于朴素基线才能通过 ML 子系统验收。未优于时模型标记为不合格、暂停 ML 调价建议并暂用基线预测以保持页面可用，但 ML 子系统和完整产品不得标记为验收完成。
- 升级路线（可选）：LSTM / LightGBM，接口保持一致。

### UC-M-03 输出与回写

预测结果由 ML 子进程通过内部接口回写：电站 ID、预测生成时间、目标时间、预测充电量、预测空闲桩数、是否高峰。管理端与大屏只通过受权 REST 接口读取结果。

预测繁忙数按预测负荷除以最近 30 天单台繁忙设备小时均量后向上取整并限制到可运营设备数，预测空闲数为两者之差；预测占用率达到 80% 或负荷达到该站历史 90 分位数时标记高峰。

### UC-M-04 可复现性

固定随机种子；脚本支持 `--train`、`--predict`、`--evaluate` 三种模式；训练产物保存为 `ml/models/load_rf.pkl`。

同时最多运行一个训练任务和一个预测任务，超时分别为 10 分钟和 2 分钟；重复请求返回当前任务。模型缺失时使用朴素基线，失败保留最近成功结果并标记过期；模型保留 30 天，预测和评估历史保留 90 天。

## 8. 非功能需求（NFR）

| 编号       | 类别   | 要求                                       |
| -------- | ---- | ---------------------------------------- |
| NFR-P-01 | 性能   | 电站列表（≤100 站）加载渲染 < 500ms                 |
| NFR-P-02 | 性能   | 营收图表（30 天聚合）查询 < 300ms                   |
| NFR-P-03 | 性能   | 充电中页面每秒刷新，CPU 占用 < 5%                    |
| NFR-P-04 | 容量   | 支持 3,000 个注册账号、100 个同时在线连接、50 个同时排队流程和 48 个同时充电会话 |
| NFR-P-05 | 吞吐   | HTTPS API 持续处理 20 请求/秒，并承受 50 请求/秒短时峰值；WebSocket 支持 100 个在线会话 |
| NFR-U-01 | 易用性  | 所有失败操作必须有明确文字提示，不允许静默失败                  |
| NFR-U-02 | 易用性  | Qt Widgets 用户端验收窗口固定为 420×760；可额外适配字体缩放但不得改变基准截图尺寸，管理端最小 1280×800 |
| NFR-C-01 | 可移植性 | 同一份 CMake 工程统一使用 Qt 6.2，在 Windows 10/11（MSVC 2019/2022）与 Ubuntu 22.04+（GCC 11+）均可编译，不含无等价封装的平台专有 API |
| NFR-C-02 | 可移植性 | 所有路径使用 `QDir`/`QStandardPaths` 拼接，禁止硬编码盘符与反斜杠 |
| NFR-C-03 | 可移植性 | 源文件统一 UTF-8 编码，MSVC 下加 `/utf-8` 选项       |
| NFR-C-04 | 并发/可移植性 | 仅在真实业务中使用 `QThread`、`QThreadPool`、Qt 异步事件和 `QProcess`；数据库连接仅归属 Crow 服务端专用工作线程，所有耗时任务不得阻塞 UI 或服务器事件循环，后台线程不得直接操作 UI |
| NFR-M-01 | 可维护性 | 单个源文件不超过 400 行，超出必须拆分                    |
| NFR-M-02 | 可维护性 | UI、Controller、应用服务和领域层不出现 SQL；SQL 仅存在于 `infrastructure/sqlite` 数据访问实现 |
| NFR-M-03 | 可维护性 | 所有数据库访问使用参数化查询（`bindValue`），禁止字符串拼接 SQL  |
| NFR-M-04 | 可维护性 | 日志统一写入 `logs/ncs_YYYYMMDD.log`，包含级别、时间、模块和请求 ID；应用日志保留 30 天，审计/运维日志保留 180 天 |
| NFR-S-01 | 安全性  | 用户和管理员密码使用专用密码哈希，优先 Argon2id；默认演示密码只允许开发配置 |
| NFR-S-02 | 安全性  | 界面展示手机号时中间 4 位打码                         |
| NFR-S-03 | 安全性  | SQLite 文件仅允许同机 `ncs_server` 和授权开发人员访问，客户端不得打开，不提交 Git、不放在网络共享目录 |
| NFR-S-04 | 安全性  | 普通用户会话最长 30 天且最多 3 个桌面终端；管理员最多 2 个终端，退出或注销立即撤销会话 |
| NFR-S-05 | 安全性  | 队列和预约通过鉴权 WebSocket 站内通知，通知不含手机号、余额或完整订单；Android 系统推送不属于当前验收范围 |
| NFR-R-01 | 可靠性  | 程序异常退出后重启，充电中订单可恢复继续计费                   |
| NFR-R-02 | 可靠性  | SQLite 打开失败、文件损坏、版本不匹配、锁超时或事务失败时给出明确提示而非崩溃或静默丢数据 |
| NFR-R-03 | 可靠性  | Crow 服务端使用 SQLite 在线备份生成一致性快照，每日保留 7 份、每周保留 4 份并可加密同步云服务器；RPO 24 小时、RTO 4 小时 |
| NFR-D-01 | 部署   | 开发/验收 VM 推荐 2 核/4GB/40GB；Crow HTTPS/WebSocket 仅监听受控本机或 VM 网络接口，不要求公网暴露 |
| NFR-D-02 | 部署   | 严格验收时用户端、PC 管理端、Crow 服务端和 SQLite 在同一 Ubuntu VM 运行；VM 使用 NAT，跨机器模式属于远期扩展且不得共享 SQLite 文件 |

容量与并发测试不得依赖真实用户。测试环境使用独立 SQLite 文件和仅在测试配置启用的模拟账号，由 Python `asyncio` HTTP/WebSocket 虚拟客户端连接 Crow 服务，并构造 50 个排队流程和最多 48 个充电会话。测试环境禁用外部通知；测试结束后删除并重建测试库，不把测试账号或固定密码用于正式演示。
