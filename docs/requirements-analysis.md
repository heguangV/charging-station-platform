# NCS 充电桩管理平台需求分析

## 1. 单一产品目标

本项目当前只建设一套可验收的桌面系统。系统以 [软件需求规格说明书](01-requirements-specification.md) 的文字功能、异常流、业务规则、非功能指标和交付内容为主体；只有在能显著改善数据一致性、安全性或可维护性时，才采用不降低原验收效果的等价技术替换。

详细需求冲突、仍未确定的规则和下一步问题统一维护在 [需求决策与未确定问题](requirements-gap-analysis.md)。实现具体功能时必须回查对应 `UC-*`、`BR-*` 和 `NFR-*`，不能只依赖本文摘要。

### 1.1 需求基线与冲突裁决

- [软件需求规格说明书](01-requirements-specification.md) 是项目的最低交付与验收基线，其中的功能、异常流、业务规则、非功能指标和验收清单不得被后续讨论、需求分析摘要、Skill、设计或代码弱化。
- 后续决定只有在补充新能力、提高指标，或以可验证的等价方案完整保留原有行为和验收结果时才有效；“暂不需要”“可选”“不阻塞发布”“只做其中一部分”等表述不能取消说明书已经要求的内容。
- 发生冲突时采用能够同时满足各项要求的更严格表述；无法兼容时以说明书原要求为准，并把冲突记录到需求决策文档，不得静默选择较弱方案。
- 等价替换必须在需求追踪中记录原条款、替换理由、保留的可观察行为和验证证据。若尚不能证明等价或更高，则按原方案和原验收标准实现。

项目定位仍是教学、团队研发和功能演示系统：使用模拟充电桩、虚拟钱包和模拟支付，不连接真实电力设备，不处理真实资金。

## 2. 最终系统组成

| 子系统 | 最终技术与形态 | 主要职责 |
| --- | --- | --- |
| 车主用户端 | Linux Qt Widgets + C++，固定 420×760 竖屏桌面 GUI | 登录、地图、导航、资料、充值、排队/预约、充电、结算、订单 |
| PC 服务器端（管理端） | Linux Qt Widgets + Qt Charts + `QTcpServer` | 营收、设备、站点、用户、订单、运维、预测管理及 Socket 服务 |
| 主数据库 | SQLite 3 + Qt SQL/QSQLITE，单文件 `charge_platform.db` | 账号、站点、设备、队列、订单、计费、钱包、日志和预测数据 |
| 数据大屏 | Vue 3 + ECharts | 1920×1080 运营与预测看板 |
| 智能分析 | Python 3.10+ + scikit-learn | 数据聚合、训练、评估、预测和结果回写 |

开发环境使用 VMware 17、Ubuntu 22.04 或更高版本、Qt Creator 6.2+、Qt 6.5.3+、CMake、Ninja、C++17 和 Qt SQLite 驱动；当前验证版本为 Qt 6.8.3。桌面 C++ 工程能在 Windows 10/11（MSVC 2019/2022）与 Ubuntu 22.04+（GCC 11+）构建；交付验收以 Ubuntu 22.04+ 为主。

## 3. 等价增强决策

| SRS 原方案 | 最终方案 | 替换理由 | 必须保持的行为 |
| --- | --- | --- | --- |
| Qt Widgets 手机竖屏用户端 | 保持 Qt Widgets，固定 420×760 | 直接遵循说明书，先完成桌面验收 | 所有 `UC-U` 页面、异常流和竖屏交互 |
| 两个程序共享 SQLite 文件 | `ncs_user` 与 `ncs_admin` 通过公共数据层访问同一文件，`ncs_admin` 同时承载 `QTcpServer` | 同时满足详细 SRS 的共享数据库和基础说明的 Socket/多线程要求 | WAL、外键、事务、初始化、种子和恢复 |
| 大屏轮询本地 JSON | 服务端原子导出 `dashboard.json`，前端每 30 秒拉取 | 直接遵循说明书且保持进程解耦 | 原布局、刷新周期、数据截止时间和空数据处理 |
| SQLite 元/本地时间字段 | SQLite 保存整数分和 UTC ISO 8601 文本，界面显示元和本地时间 | 避免金额累计与跨日期统计误差 | 所有金额范围、公式、小票和本地时间语义一致 |
| 加盐 SHA-256 管理员密码 | 专用密码哈希，优先 Argon2id；不可用时使用成熟等价方案 | 提高账号安全 | 开发演示账号、错误提示和锁定规则保留 |
| 基础说明书的 Linux 并发学习要求 | 在数据库、耗时任务、Socket 和 ML 等真实业务中使用 Qt 并发与异步机制 | 保持跨平台并避免无业务价值的演示程序 | 主框架具备多线程能力，UI 和服务器事件循环不被耗时任务阻塞 |

腾讯地图、RandomForest、Qt Charts、Haversine、ECharts 和 SRS 指定的核心业务流程不替换。

## 4. 用户角色与权限

最终保持三类角色，不能把说明书中的决策查看能力合并后删除：

| 角色 | 权限 |
| --- | --- |
| 车主用户 | 使用 Linux Qt Widgets 竖屏用户端管理自己的资料、钱包、排队、预约、充电和订单 |
| 运营管理员 | 使用 PC 管理端管理站点、设备、用户、订单、价格和运维，并使用管理员账号访问 Web 数据大屏、营收与预测信息 |
| 决策查看者 | 使用只读账号访问 Web 数据大屏，查看运营与预测信息，不具备价格、设备、用户或订单修改权限 |

权限由公共业务服务层和 PC 服务器端共同校验，不能仅依靠界面隐藏按钮。首次初始化按说明书生成 `admin / 123456` 开发验收账号；验收完成后或正式演示前必须修改默认密码。

## 5. 全局业务规则

- 手机号必须为以 1 开头的 11 位数字且全局唯一；用户名也全局唯一。
- 一个用户同一时间最多有一个排队、待确认、已预约或充电中的活动流程。
- 一个充电桩同一时间最多被一个待确认分配、预约或充电会话占用。
- 余额达到全市统一最低起充金额 5.00 元才能预约或开始充电。
- 故障、重启中、停用设备不能被分配、预约或开始充电。
- 金额使用整数分，电量使用明确精度的定点 kWh，时间在 SQLite 中保存 UTC ISO 8601 文本并在界面显示本地时间。
- 预约、设备分配、开始、结束、结算、充值、余额调整和运维命令必须支持事务、幂等和审计。
- 订单、充电会话和钱包流水不物理删除；账号注销后匿名保留必要业务凭证。
- `charge_platform.db` 是设备、排队、订单、计费与余额的唯一可信来源；用户端和管理端都只能通过公共 `core/database` 与 `core/service` 层执行参数化查询和事务，UI 不得包含 SQL。

## 6. 账号、登录和用户中心

### 6.1 注册与登录

- 用户注册时填写唯一用户名、11 位手机号和密码；手机号由必填改为遵循 SRS 的必填规则。
- 支持“用户名 + 密码”或“手机号 + 密码”登录。
- 为覆盖 SRS 的验证码自动注册演示，提供 6 位模拟验证码流程：获取后按钮倒计时 60 秒，验证码直接显示在开发界面。
- 模拟验证码默认 10 分钟有效、最多尝试 5 次，获取新码后旧码立即失效。
- 60 秒内不得重复获取验证码；验证码只能显示在当前本地开发会话中，不得写入日志。
- 冻结用户不能登录或发起新充电；登录失败必须给出统一、安全的提示。
- 只有绑定手机号的用户可以使用模拟验证码重置密码。

### 6.2 用户资料

- 新用户默认余额为 0，默认昵称为“用户 + 手机号后 4 位”，显示默认灰色头像。
- 展示头像、昵称、脱敏手机号、钱包余额和注册时间。
- 昵称长度 1～20，禁止纯空白。
- 头像支持 PNG/JPG/JPEG/BMP，最大 5MB；文件复制到 `QStandardPaths` 确定的共享 `avatars/` 目录，数据库保存相对路径。
- 修改资料后立即持久化并能在重新登录后恢复。
- 用户可退出登录和申请注销；注销撤销全部令牌并清除手机号、密码等登录凭据。
- 注销时立即匿名化用户名和手机号，头像文件在 24 小时内删除；匿名订单、钱包和充电记录保留 3 年，审计/运维日志保留 180 天，匿名 ML 聚合数据保留 1 年。

### 6.3 虚拟钱包

- 模拟充值范围 0.01～10000 元，最多两位小数，不调用真实支付。
- 每次充值、扣费、退款、欠费和管理员调整均产生不可变钱包流水。
- 欠费用户仍可登录、查看订单和充值，但不得加入队列、创建预约或开始新充电；充值在同一事务内优先清偿欠费，剩余金额才进入虚拟余额，并分别生成清偿与入账流水。
- 欠费清零后，如账号未冻结或注销，公共业务服务层自动恢复新充电权限；充值不足时余额保持 0，剩余欠费相应减少。
- 管理员调整必须填写原因并记录审计日志。
- 页面明确标注“虚拟余额”，不支持提现。

## 8. 排队、预约、充电与结算

### 8.1 排队与预约

- 有兼容空闲设备时，用户可以直接预约；预约保留 15 分钟，超时未开始则取消并释放设备。
- 没有空闲设备时按“站点 + 快充/慢充类型”进入即时队列，不支持选择未来日期或时间段预约，也不允许指定某一台设备排队。
- 同类型任一设备释放后，公共业务服务层在 SQLite 事务中按入队顺序分配最先可用的兼容设备。
- 队列轮到用户后通过 Socket 消息和用户端站内提示通知，并提供 5 分钟确认期。
- 入队时展示当前预估价和最高浮动范围；轮到用户时生成包含电费、基础服务费、排队浮动和总单价的最终报价，并在 5 分钟确认期内锁定。
- 用户确认分配后按锁定报价创建 15 分钟预约；拒绝或 5 分钟未确认不产生费用，报价与设备分配失效并递补下一位。
- 有空闲设备直接预约时，在预约成功事务中立即保存同样结构的价格快照。
- 用户可在排队等待、5 分钟报价确认和 15 分钟预约阶段主动取消；系统立即移除活动流程、释放设备并递补下一位，不收取费用。
- 充电开始后不再提供“取消”，只能结束充电并按实际电量结算；重复取消请求必须幂等，不得重复释放或写入多条取消记录。
- 第一版不设置取消次数限制或违约处罚，但记录取消阶段、原因和服务端时间用于统计。
- 运营管理员可以二次确认后强制释放待确认或已预约设备，但必须填写原因并选择设备回到空闲、故障或停用；用户流程取消且不自动重新排队，通知提供重新排队入口。该操作不收费并完整审计，充电中设备禁止强制释放。
- 队列顺序、设备分配和倒计时均以 PC 服务器端时间为准。

活动流程的数据库状态码/协议名称固定为：`10/QUEUED`、`20/QUOTE_PENDING`、`30/RESERVED`、`40/CHARGING`、`50/SETTLING`、`60/COMPLETED`、`70/CANCELLED`、`80/SETTLEMENT_FAILED` 和 `90/EXPIRED`。具体取消、超时和管理员原因单独保存。

### 8.2 充电前拦截

- 进入选桩前查询排队、待确认、预约、充电中和待结算状态。
- 已充电中的用户进入当前充电控制页继续计费；待结算用户强制进入结算页。
- 其他活动状态进入对应队列或预约页，不允许重复创建流程。

### 8.3 实时充电

- 开始充电时记录价格与时间倍率快照，订单/会话进入充电中状态。
- 每秒展示时长、电量、费用、实时功率和模拟 SoC。
- 电量按功率和模拟时长累积；时间倍率默认 60、可配置范围 1～300，只影响新会话。
- 用户端退出或 Socket 断开后，PC 服务器端继续计费；重新连接后从 SQLite 恢复正确状态。
- 用户可以手动结束，也可以设置不限金额、10/20/30 元或 1～500 元目标金额自动结束。

### 8.4 价格与结算

- 北京当前按行政区进行基础定价，站点根据腾讯地图行政区编码 `adcode` 归区；区域分别保存电费单价和服务费单价，不提供全市一键同步价格，数据库保留未来自定义价格区域的能力。

| 行政区 | 电费（分/度） | 基础服务费（分/度） | 基础总价（元/度） |
| --- | ---: | ---: | ---: |
| 海淀区 | 85 | 50 | 1.35 |
| 朝阳区 | 90 | 55 | 1.45 |
| 丰台区 | 80 | 45 | 1.25 |
| 石景山区 | 75 | 40 | 1.15 |
| 通州区 | 70 | 35 | 1.05 |

- 排队人数按确定性阶梯规则自动影响服务费，电费保持分区基础价稳定；机器学习只给出未来 1/6/24 小时的价格浮动趋势、建议幅度和原因，须经运营管理员确认后生效。
- 排队压力为“等待人数 ÷ 当前可运营的同类型设备数”，故障、停用和重启中设备不计入分母；压力 `≤0.5` 不调整、`(0.5,1]` 上浮 10%、`(1,2]` 上浮 20%、`>2` 上浮 30%。
- 队列服务费每 5 分钟重新计算，可以随压力回落但不低于区域基础服务费；自动调价和管理员采纳 ML 建议都记录原价、新价、触发原因、操作者与生效时间。
- 管理员采纳的 ML 调整范围为 `-20%～+20%`、步长 5%，有效期可选 1/6/24 小时并在到期后自动失效；最终服务费按 `基础服务费 × (1 + ML 调整比例 + 排队调整比例)` 计算，并限制在基础服务费的 80%～140%，按分/度四舍五入保存。
- 价格快照一经保存，后续区域价格、排队压力和 ML 建议变化均不影响该次预约、充电与结算。
- `电费 = 电量 × 电费单价`，`服务费 = 电量 × 服务费单价`，总额为两者之和。
- 系统在预计达到目标金额或余额上限时自动停止，正常流程不产生欠费。
- 因计时步长或并发造成少量超额时，余额扣至 0，并记录欠费金额，保留 SRS 的兜底规则。
- 结束时在同一事务内写订单、释放设备、更新设备累计次数/时长、扣减余额和生成流水；任一步失败整体回滚。
- 小票显示订单号、站点、设备、起止时间、时长、电量、费用明细、总额和余额。
- 历史订单按时间倒序，可查看详情和状态。

## 9. PC 管理端

### 9.1 界面与登录

- 使用 `QMainWindow`、左侧导航、右侧 `QStackedWidget`、顶部刷新/退出和底部状态栏。
- 最小分辨率 1280×800，深色科技风可参考原说明图片但不要求复刻。
- 管理员账号密码错误使用统一提示；连续失败 5 次锁定登录 30 秒。

### 9.2 营收与状态

- 显示今日、本月、总营收，只统计已完成订单。
- 近 7/30 日营收折线图和同期每日订单量柱状图；无数据时显示空坐标与提示。
- 显示空闲、使用中、故障状态数量、比例和饼图。
- 设备健康度 = `(空闲 + 使用中) / 总数 × 100%`。

### 9.3 设备、站点、用户与订单

- 设备列表、筛选、编号搜索、新增、故障/恢复、模拟远程重启和受控删除。
- 空闲或故障设备经二次确认后可以立即模拟重启，显示 2 秒进度并写运维日志。
- 待确认分配、已预约或待结算设备优先登记“释放后自动重启”；确需立即处理时先执行对应的受控释放流程。
- 充电中设备保留说明书要求的紧急远程重启能力：管理员必须二次确认并填写原因，管理端先停止计费、按已产生电量完成幂等结算或生成待处理结算、通过 Socket 通知用户并记录审计，然后模拟重启；任一步失败不得直接释放设备或丢失订单数据。
- 对待确认或已预约设备另提供受控“强制释放”操作，遵循二次确认、必填原因、目标状态选择、用户通知和审计规则；它不等同于强制重启，也不得作用于充电中设备。
- 重启命令记录管理员、原因、创建时间、执行时间和结果；重启中设备不得参与预约或排队分配。
- 站点支持新增、修改和受控删除；新增站点可以批量生成设备，经纬度必须合法。
- 有设备或历史业务数据的站点不物理删除，改为停用。
- 用户支持手机号模糊搜索、冻结/解冻和订单历史查看。
- 冻结用户不终止进行中的充电，但仍允许查看、结束和结算；禁止创建新流程。
- 订单支持按编号、用户、站点、设备、状态和时间查询。

### 9.4 智能预测

- 展示各站未来 1/6/24 小时预测负荷、空闲桩数和高峰标记。
- 对比历史实际与预测曲线。
- 管理端使用 `QProcess` 启动 Python 任务；失败时提示并保留上一次成功结果。

## 10. 数据库与种子数据

SQLite 数据库至少包含以下领域数据：

- 用户、角色、管理员、登录会话和验证码。
- 充电站、充电桩、设备状态历史、设备命令和运维日志。
- 排队项、待确认分配、预约、充电会话、订单和计费明细。
- 钱包账户、充值记录、钱包流水、欠费和管理员调整。
- 系统配置、审计日志、服务状态和备份记录。
- 预测样本、特征版本、模型版本、评估指标和 `load_prediction` 结果。

主数据库统一使用 SQLite 3，文件名为 `charge_platform.db`，通过 Qt `QSQLITE` 驱动访问。`ncs_user` 与 `ncs_admin` 使用同一个由配置解析出的绝对路径和公共数据库模块；任一程序首次启动时若文件不存在，则在进程间初始化锁保护下执行 `schema.sql` 和种子脚本。后续通过 `schema_version` 管理升级，已应用迁移不可修改，结构迁移与可重建演示种子分离。

- 主键优先使用 `INTEGER PRIMARY KEY`；金额和单价使用分为单位的 `INTEGER`，电量使用毫瓦时为单位的 `INTEGER`，时间使用 UTC ISO 8601 `TEXT`，状态使用 `INTEGER + CHECK`，经纬度使用 `REAL`。
- 每个数据库连接执行 `PRAGMA foreign_keys = ON`、`PRAGMA journal_mode = WAL` 和合理的 `busy_timeout`；每个进程仅由专用数据库工作线程持有连接，设备分配使用 `BEGIN IMMEDIATE`、条件更新、唯一索引和幂等键保证一致性。
- 用户端和管理端直接通过公共数据层访问同一 SQLite 文件；Socket 用于登录会话协同、实时状态、队列通知和远程运维命令，不能代替事务一致性。大屏读取原子导出的 JSON，不直接打开数据库文件。

所有结构变化使用版本化迁移，空库可以迁移并播种。种子数据固定随机种子，至少生成：

- 1 个说明书验收管理员 `admin/123456` 和 1 个只读决策查看账号；默认管理员仅用于开发/验收配置，正式演示前必须修改密码。
- 北京至少 5 个站点。
- 每站 6～12 个设备，快慢充混合，含 1～2 个故障设备。
- 生成最近 90 天的订单、充值、设备状态和负荷演示数据；管理端和大屏默认展示最近 30 天。
- 固定随机种子为 `20260901`，生成 300 个模拟车主、约 9,000 个历史订单和约 900 条充值记录；每日订单在 80～120 单间波动。
- 历史订单约 94% 已完成、6% 已取消，不生成结算失败；约 70% 使用快充、30% 使用慢充。
- 工作日高峰为 7:00～9:00 与 17:00～21:00，周末高峰为 10:00～20:00；朝阳公园、中关村、北京南站、石景山、通州运河订单占比分别为 28%、24%、22%、14%、12%。

数据库文件仅供同机 `ncs_user`、`ncs_admin` 和授权开发人员访问，不得放入 Git，也不得放在 NFS/SMB 等网络共享目录。开发、测试数据库使用不同文件。

## 11. Web 数据大屏

- Vue 3 + ECharts，1920×1080 深色单页并自适应缩放。
- 顶部显示平台名称、环境标识和实时时钟。
- 左侧显示设备状态占比和站点充电量排行。
- 中间显示总充电次数、总营收、在线设备、注册用户和近 30 日营收趋势。
- 右侧显示充电时段热力图、快慢充占比和未来 24 小时负荷预测。
- 管理端或 Python 脚本每 30 秒从 SQLite 聚合并原子替换 `web/public/data/dashboard.json`；大屏按相同周期拉取。

## 12. 机器学习智能分析

- 按“站点、日期、小时”聚合充电订单。
- 特征包含小时、星期、周末、节假日、1/24/168 小时滞后、滑动均值、站点编码和模拟天气。
- 标签为每小时充电量。
- 第一版使用 `RandomForestRegressor`，固定随机种子，无需 GPU。
- 使用按时间顺序的训练/验证/测试切分，避免数据泄漏。
- 输出 MAE、RMSE、MAPE，并与上周同一时刻朴素基线比较。
- 脚本支持 `--train`、`--predict`、`--evaluate`；模型保存在 `ml/models/load_rf.pkl`。
- Python 脚本或管理端通过公共数据层写回 SQLite，包含站点、生成时间、目标时间、负荷、空闲数和高峰标记。
- 模型或脚本失败时继续提供最近一次成功结果，并显示更新时间和失败提示。
- 模拟天气使用固定种子 `20260901`，节假日来自版本化日历；数值缺失使用训练集中位数，分类缺失记 `UNKNOWN`，不足 168 小时滞后的起始样本不参与训练。
- MAPE 只在真实值大于 0 的样本上计算并报告排除数，同时计算 WAPE。模型必须在固定测试集上优于“上周同一时刻”朴素基线才能通过 ML 子系统验收；未优于时标记不合格、暂停 ML 调价建议并暂用基线维持页面可用，但不能把 ML 子系统或完整产品标记为验收完成。
- 预测繁忙数按预测负荷除以最近 30 天单台繁忙设备小时均量后向上取整并限制到可运营设备数；预测占用率达到 80% 或负荷达到站点历史 90 分位数时标记高峰。
- 同时最多运行一个训练和一个预测任务，超时分别为 10 分钟和 2 分钟；模型缺失时使用朴素基线。模型保留 30 天，预测和评估历史保留 90 天，失败时保留最近成功结果并标记过期。

LSTM、LightGBM、设备故障诊断、调度优化和智能风控不属于当前单一目标。

## 13. 通信、并发与通知

- `ncs_admin` 承载 `QTcpServer`，`ncs_user` 使用 `QTcpSocket`；应用层消息采用“4 字节网络序长度 + UTF-8 JSON 负载”，设置最大帧长度，处理拆包、粘包、超时和异常断线。
- 协议包含版本、请求 ID、消息类型、时间和数据；响应包含稳定错误码与明确错误信息，写操作携带幂等键。
- PC 服务器端通过 Socket 推送充电、设备、队列、管理统计和预测状态；断线自动重连并从 SQLite 重新读取完整快照。
- 网络、数据库、设备模拟、文件和 ML 任务不得阻塞 UI 或服务器事件线程。
- 只在业务确有需要时使用并发：SQLite 访问由专用 `QThread` 数据库工作对象处理，CPU 密集或批处理任务使用 `QThreadPool`，Socket 使用 Qt 异步事件，ML 子进程使用 `QProcess`；后台任务不得直接操作 UI。
- 队列分配、预约到期使用用户端站内通知；Android 系统推送属于远期移动端目标。
- PC 服务器端会话使用随机不透明令牌；普通用户会话最长 30 天且最多 3 个桌面终端，管理员最多 2 个终端，退出和注销立即撤销。

## 14. 安全、错误、日志和备份

- 密码使用专用密码哈希；刷新令牌、验证码只保存安全摘要。
- 手机号展示时中间四位脱敏；日志不记录完整手机号、令牌、验证码或密钥。
- 地图、数据库备份和云凭据只存受限配置，不进入源码、GitHub 和日志。
- 所有输入、权限、状态和金额由公共业务服务层校验；数据库查询全部参数化。
- 所有失败操作提供明确文字提示；覆盖无权限、状态冲突、余额不足、数据库、网络、地图、推送和 ML 失败。
- 日志统一写入 `logs/ncs_YYYYMMDD.log`，包含时间、级别、模块和请求 ID，按日轮转。
- SQLite 使用在线备份 API 或 `VACUUM INTO` 生成一致性快照；每日保留 7 份、每周保留 4 份，并至少完成一次测试恢复。
- 应用日志保留 30 天，审计和运维日志保留 180 天；备份保存到应用受限目录并可加密同步既有云服务器。恢复目标为最多丢失 24 小时数据、4 小时内恢复。
- 严格验收拓扑在同一 Ubuntu VM 内运行 `ncs_user`、`ncs_admin` 和 SQLite 文件；VM 保持 NAT，宿主机主要用于 SSH/开发访问。跨机器模式属于远期扩展，不通过共享目录传递 SQLite 文件。

## 15. 非功能指标

- 不超过 100 个站点时，列表加载和渲染小于 500ms。
- 30 天营收聚合查询小于 300ms。
- 充电页每秒更新，在目标设备上 CPU 占用原则上小于 5%。
- 当前用户端使用 Qt Widgets，验收窗口固定为 420×760；可额外支持字体缩放，但不得改变基准截图尺寸。管理端最小 1280×800。
- 源文件使用 UTF-8，路径通过 Qt 跨平台 API 构造；MSVC 使用 `/utf-8`。
- 单个手写源文件不得超过 400 行，UI 不包含 SQL。
- 用户端、PC 服务器/管理端、大屏和 ML 都必须具备加载、空数据、失败和恢复状态。
- 当前容量目标为 100 个站点、3,000 个注册账号、100 个同时在线 Socket 连接、50 个同时排队流程和 48 个同时充电会话；管理端 Socket 服务持续处理 20 请求/秒并承受 50 请求/秒短时峰值。
- 容量验证使用独立 SQLite 测试文件和自动化虚拟用户，不依赖真实车主：Python `asyncio` TCP 客户端模拟登录、排队、预约、充电和结算，测试环境关闭外部通知。
- 并发测试必须验证最后一个空闲设备只能分配一次、同一用户不能重复进入活动流程、队列顺序稳定以及结算/扣款/释放幂等，并记录成功率、延迟、CPU、内存和数据库连接数。
