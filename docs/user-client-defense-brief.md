## 1. 我对用户端需求的理解

用户端不是管理后台，而是车主在出发前和充电过程中的移动端交互模拟。目标是让用户在 420×760 的桌面窗口中完成完整闭环：

```text
手机号登录 → 查找附近站点 → 查看并选择电桩 → 预约
→ 开始充电 → 查看实时进度 → 结束结算 → 查看订单/余额
```

关键业务约束：用户不能同时创建多个未完成流程；只有空闲电桩可选；预约有倒计时且可取消；充电数据按秒刷新；结算需要二次确认；余额不足、桩不可用、未完成订单和网络失败均需要给用户可理解的反馈。

客户端不实现原生 TCP/UDP，也不打开 SQLite；业务真相、金额计算、订单状态变迁和并发控制由后端负责。

## 3. 技术选型及理由

| 技术 | 用途 | 选择理由 |
| --- | --- | --- |
| C++17 + Qt 6.2 Widgets | 桌面模拟手机端 UI | 当前 Ubuntu 环境可运行，窗口、信号槽、定时器和 QSS 足以支持验收演示 |
| CMake | 构建 | 与团队工程统一，便于多端目标集成 |
| QNetworkAccessManager | HTTPS REST 异步请求 | Qt 原生、非阻塞 GUI、可统一处理 Token/超时/错误 |
| MockUserClientService | 离线演示数据源 | 后端不可用时仍可完成录屏、截图和主流程演示 |
| QTimer | 倒计时与进度刷新触发 | Mock 中驱动演示；REST 模式中应每秒异步请求 progress |
| QSS + 自绘组件 | 主题、SoC 环形仪表、Dock 动效 | 不引入不稳定的外部 UI 库，保持 Qt 6.2 可用和可维护 |

## 4. 代码结构设计

```text
apps/user/
├── main.cpp                         # 应用启动、配置、Mock 注入、REST 探测入口
├── user_main_window.*               # 页面容器、主流程状态与导航
├── user_main_window_login.cpp       # 手机号登录与验证码交互
├── user_main_window_navigation.cpp  # 路线方式与浏览器降级
├── user_main_window_orders.cpp      # 订单列表、空状态、小票入口
├── user_main_window_profile.cpp     # 头像、昵称、充值、退出
├── user_main_window_state.cpp       # 页面刷新、Toast、Esc 返回规则
├── user_demo_service.*              # 领域模型、Service 抽象、Mock 状态机
├── net/
│   ├── api_client.*                 # HTTP、Token、超时、统一响应信封
│   └── user_api.*                   # 唯一持有 /api/v1/user 路径的封装
└── ui/
    ├── app_theme.*                  # 统一配色、卡片和滚动条主题
    ├── bottom_navigation.*          # 首页/订单/我的 Dock 与微动效
    ├── station_list_widget.*        # 站点搜索、筛选、滚动列表
    ├── station_card.*               # 电站实体卡片
    ├── charger_table.*              # 电桩选择卡片
    └── charge_soc_gauge.*           # 自绘 SoC 环形仪表
```

数据路径应这样解释：

```text
Widget/Page → UserClientService → MockUserClientService（当前演示）
                               └→ UserApi → ApiClient → HTTPS REST（后续联调）
```

UI 只显示领域模型并发送用户操作；它不出现 SQL、JSON 字段名和 URL。`ApiClient` 负责统一添加 `Authorization`、`X-Request-ID`，写操作添加 `Idempotency-Key`，并将响应统一为 `ApiReply`。

## 10. 高频提问与回答

**为什么用 Mock？**  后端与客户端并行开发，Mock 保证验收演示和 UI 迭代不被服务端进度阻塞；它实现相同的领域模型接口，后续只替换数据源，不重写页面。

**为什么客户端不直接连数据库？**  SQLite 的事务、余额扣减、并发抢桩和订单状态必须由服务端统一控制；直连会破坏权限边界和数据一致性。

**如何避免重复点击导致重复扣款？**  UI 先禁用结算按钮；客户端给写请求加 `Idempotency-Key`；服务端以同一键返回同一结算结果，三层共同保障。

**实时数据怎么实现？**  当前 Mock 用 QTimer 演示变化；正式模式每秒异步轮询 `GET /flows/{flowNo}/progress`，后续可消费 WebSocket 事件，但 REST 快照仍用于首屏和断线恢复。

**为什么不直接用成熟 UI 库？**  项目需要保证 Ubuntu Qt 6.2 可运行、依赖可控；因此使用自有 QSS/小组件实现一致的卡片、Dock、状态色和仪表，避免版本或授权风险。

**你的创新点落在哪里？**  不在客户端伪造结论：后端/ML 提供可解释的推荐、低碳和预测数据；客户端把推荐原因、预算和行动入口呈现给用户。
